** Why this session exists **

The user has real users of the package running the thesis-era `main`
branch (mizerReef 1.x -- I'll call this "v1" below). `major_update`
(this branch, DESCRIPTION Version: 2.1.0, "v2") is close to release and
is a structural rewrite: reef behaviour used to be wired in via direct
`@rates_funcs` name overrides (`reefEncounter`, `reefFeedingLevel`,
`reefPredMort`, `reefMort`, `reefRates`); it's now wired in via S3
dispatch on a `mizerReef` marker class chained through mizer's
extension-registration system (`project*.mizerReef` methods in
R/reef-project_methods.R, see vignettes/extension_mechanism.Rmd). A
real v1 object handed to v2 code will not error immediately (the old
`reef*` functions still exist) but will silently run the OLD code path
and bypass every behavioural fix/change made in this branch. The user
wants a function users can call once, on their existing tuned v1
params object, to bring it up to the v2 structural layout WITHOUT
losing their tuned model or having it silently re-tune itself. This
needs to ship before the release, and needs a NEWS.md entry so users
actually see it.

There's a memory file from a previous session
([[project-upgradeparams-v1-to-v2]] in this project's Claude memory)
with a lot of pre-gathered context on this exact question. Per the
user's explicit instruction this session, I treated that as a
starting point, not ground truth, and re-verified everything myself
against the live code and real bundled v1 objects before acting on it
-- some of it (e.g. the existence and behaviour of an already-nested
`refuge_params`/`use_dummy_fish_bins` in v2, and the exact algae/detritus
component vs. "_params" echo split) needed more precision than the
memory captured, and one thing (the algae/detritus "_params" echo lists
being genuinely stale/unused by the live dynamics, not just a
duplication smell) was a new finding this session.

** The exact structural diff, v1 -> v2 (verified against real objects, not guessed) **

- **Class**: v1 = plain S4 `"MizerParams"`. v2 = `"mizerReef"`, set via
  `params@extensions <- mizer::getRegisteredExtensions(); params <-
  mizer::coerceToExtensionClass(params)` at the end of `newReefParams()`.
  A genuine v1 object's `@extensions` is `character(0)` -- it was never
  registered, so mizer's own automatic `upgrade.mizerReef()` S3 hook
  (fired via `runExtensionUpgrades()` inside `validParams()`) never
  fires for it. That hook (already implemented in this file, see
  `upgrade.mizerReef()` above/below) only handles a DIFFERENT, smaller,
  already-registered-extension migration (old direct S4
  slots -> `other_params` sub-lists, some earlier point in this
  branch's own history) -- it is not sufficient for the v1 cold-start
  case and I left it untouched.

- **`@rates_funcs`**: v1 has `Rates="reefRates"`,
  `Encounter="reefEncounter"`, `FeedingLevel="reefFeedingLevel"`,
  `PredMort="reefPredMort"`, `Mort="reefMort"` (direct overrides). v2
  leaves all five at mizer's stock defaults (`mizerRates`,
  `mizerEncounter`, `mizerFeedingLevel`, `mizerPredMort`, `mizerMort`)
  and gets reef behaviour via S3 dispatch instead. All other
  `@rates_funcs` entries (EReproAndGrowth, PredRate, FMort, ERepro,
  EGrowth, ResourceMort, RDI, RDD) were already mizer stock in v1 too --
  only reset the five reef-specific ones, don't touch the rest (in case
  a user customised RDD, etc.).

- **`species_params$bad_pred` -> `blocked_pred`**: straight rename,
  confirmed present under the old name on both bundled v1 objects.

- **Core mizer-level slot drift** (unrelated to mizerReef, just normal
  mizer version drift -- e.g. karpata_model's `mizer_version` is
  "2.5.0", current mizer is 3.2.0, and its `@rates_funcs` is missing
  the newer `Diffusion` entry entirely): don't hand-roll this. Calling
  `mizer::validParams()` on the raw v1 object already triggers mizer's
  own internal `upgrade.MizerParams()` correctly and safely -- verified
  it leaves every reef-specific `other_params`/`species_params` column
  completely untouched (mizer's upgrade code has zero knowledge of
  mizerReef's fields) while fixing `Diffusion`, `mizer_version`, etc.
  `upgradeReefParams()` calls `mizer::validParams()` itself (exported,
  not an internal `:::` call) at the start, before touching anything
  reef-specific, and again at the end after class promotion.

- **`other_params$algae`/`other_params$detritus` (the LIVE, authoritative
  component-params lists consumed directly by `algae_dynamics()`/
  `detritus_dynamics()` via `other_dynamics`/`other_encounter`, see
  R/reef-components.R:27 `params@other_params[[component]]$rho`)**:
  same keys and same nesting in both v1 and v2 for the non-carrying-
  capacity case (`rho`, `growth` for algae; `rho`, `sen_decomp`,
  `ext_decomp`, `external` for detritus) EXCEPT v2's `newReefParams()`
  unconditionally adds a `capacity` key to both (confirmed against a
  freshly-built v2 object) that v1 only added when carrying capacity
  was turned on via the (separate, opt-in) `setURcapacity()`. Migration
  adds this key using the preserved `algae_capacity`/`detritus_capacity`
  value (or 1, matching `newReefParams()`'s own non-cc default) so the
  migrated object matches the current schema exactly.

- **`other_params$algae_params`/`other_params$detritus_params` (the
  "config echo" lists written once by `setAlgaeParams()`/
  `setDetritusParams()`, NOT read by the live dynamics functions)**:
  new in v2, don't exist in v1 at all. IMPORTANT finding this session:
  on the real bundled `caribbean_3_model`, these are already stale/out
  of sync with the live `algae`/`detritus` lists (`algae_params$algae_growth`
  = 2000, the untuned literature default, while the live
  `algae$growth` = 86.9, the actual tuned value the model runs on;
  `detritus_params$external` = -885 vs. live `detritus$external` =
  -120) -- `reefSteady()`/`tuneUR()` update the live component but
  never touch this echo. So these lists are structurally required
  (`newReefParams()` always creates them) but NOT the source of truth
  and NOT safe to treat as authoritative for anything. `upgradeReefParams()`
  populates them by calling the real `setAlgaeParams()`/
  `setDetritusParams()` with the PRESERVED v1 tuned values (not
  defaults) so they start in sync, but the live `algae`/`detritus`
  lists remain the actual source of truth exactly as in every existing
  v2 object.

- **`other_params$refuge_params`**: v1 has this as a 1-row data.frame
  with just `method`, `a_bar`, `b_bar`, `w_settle`, `max_protect`,
  `tau` -- everything else refuge-related
  (`method_params`, `refuge`, `bin.id`, `refuge_lengths`, `degrade`,
  and for degrade=TRUE objects, `t_bleach`/`trajectory`/`deg_scale`,
  confirmed by reading v1's `setDegradation()`/`setURcapacity()`
  source directly in the worktree) lives at the TOP LEVEL of
  `other_params` instead. v2 nests everything inside
  `refuge_params` (confirmed against both a fresh build and
  R/reef-project_methods.R's actual field reads, e.g.
  `params@other_params$refuge_params$method_params`,
  `...$refuge_params$degrade`, `...$refuge_params$bin.id`) and adds one
  genuinely new field, `use_dummy_fish_bins`, which didn't exist as a
  concept in v1 -- v1's `getRefuge()` always used the shared
  `a_bar`/`b_bar` dummy-fish conversion, so `TRUE` (the current
  default, explicitly documented as "legacy behavior") is the correct,
  behaviour-preserving value for migrated objects, not a guess.
  `upgradeReefParams()` rebuilds this whole nested structure by calling
  the real `setRefuge()` + `getRefuge()` with the preserved
  method/method_params/a_bar/b_bar/w_settle/max_protect/tau (and
  preserved refuge_user/blocked_pred/satiation, which are already
  present as species_params columns so setRefuge()'s "only fill in if
  missing" branches leave them untouched) -- this recomputes
  `refuge`/`bin.id`/`refuge_lengths` from those same preserved inputs
  using the CURRENT, presumably bug-fixed logic, rather than carrying
  over v1's raw computed matrices as-is. I judged this as a structural
  recomputation (same inputs, current code), not a silent recalibration,
  since none of the actual tunable numbers change. If `degrade` was
  TRUE, `t_bleach`/`trajectory`/`deg_scale` are relocated into
  `refuge_params` too (same rename-and-relocate treatment) -- flagged
  with an extra warning since neither bundled v1 test object actually
  has `degrade = TRUE`, so this specific path is verified against
  source reading only, not a real object.

- **`ext_mort_params`, `include_sen_mort`, `new_refuge`**: same names,
  same shape, top-level in both v1 and v2 -- carried over unchanged.

- **Explicitly NOT carried over** (stale v1-only bookkeeping,
  superseded in v2, per this session's design decision and the prior
  session's memory note): top-level `other_params$initial_algae_growth`
  and `other_params$initial_d_external` (the ORIGINAL pre-tuning input
  values, not the live tuned ones -- keeping them would just be more of
  the same "duplicate value goes stale" pattern already found once this
  session). Top-level `algae_capacity`/`detritus_capacity`/
  `carry_capacity` are read once during migration then dropped (their
  values live on in `algae_params$algae_capacity`/
  `detritus_params$detritus_capacity`/`other_params$use_UR_cc` instead).

** Explicit design decision: preserve tuned values, don't re-tune **

`algae_growth`, `detritus_external`, capacities, refuge
method/method_params -- all migrated as-is from the v1 object, not
reset to v2's literature-default constants and not silently re-run
through `reefSteady()`/`tuneUR()`. Per the prior session's memory note
and my own judgement: retuning is a calibration decision that needs
the user's domain judgement (e.g. `caribbean_10_model`'s NEWS.md entry
this session's history shows exactly this kind of silent staleness
biting the project before), not something an upgrade function should
decide unilaterally. `upgradeReefParams()` ends with `warning()` calls
(not just message()/docs) telling the user: (a) it reset the old
direct rate-function overrides to the new S3-dispatch defaults (a real
behavioural change, not just a rename) and (b) the migrated object
carries over the OLD tuning values as-is and is not guaranteed to be a
genuine joint steady state under the current (fixed) algae/detritus
mechanism -- they should consider running `reefSteady()` themselves.

** Naming **

Per the prior session's memory note (the user explicitly raised this
closing out that session): named `upgradeReefParams()`, not
`upgradeParams()` or `upgradeParams.mizerReef()`, specifically so it
doesn't collide with or get confused for `mizer::upgradeParams()`
(which is internal/unexported anyway, `mizer:::upgradeParams`) or the
automatic `upgrade.mizerReef()` S3 hook already in this file (which
only fires for already-registered v2.x objects and is unrelated to
this cold-start v1 case). `upgradeReefParams()` finishes by registering
the extension and promoting the class exactly like `newReefParams()`
does, so any *future* v2.x -> v2.y micro-upgrade then works
automatically via the standard hook without the user ever needing to
call `upgradeReefParams()` again.

** Round 2 (the user's three follow-ups on item 8, WITH code/doc
changes) **

1. "I think I used getAlgaeConsumption() as a different function than
   algae_consumption() for a reason... it's the same pattern detritus
   uses, right? It emulates mizerShelf?" -- CONFIRMED, by reading
   mizerShelf's actual installed source directly (v1.0.2, found at
   find.package("mizerShelf")): mizerShelf has the identical
   x_consumption() [mass-specific, used in dynamics AND in its tuning
   function tune_carrion_detritus()] / getXConsumption() [total
   per-species, diagnostic-only] split, and critically its tuning
   function uses the PLAIN mass-specific function, never the getX()
   wrapper -- exactly the pattern the 31/07 fix switched tuneUR() to
   for algae. So last night's fix (algae_consumption() instead of
   getAlgaeConsumption() inside tuneUR()) is the CORRECT, mizerShelf-
   consistent choice, not a deviation from it. No code change needed
   here, only documented the reasoning (see item 2's commit).

2. "Fix the roxygen documentation for detritus components to match
   the code. Research the satiation mechanic thoroughly first, and
   check whether it's described correctly." Satiation mechanic fully
   traced: species_params$satiation (default: FALSE for carnivores,
   TRUE for pure resource consumers -- see setRefuge()'s existing,
   accurate docs) is read by projectFeedingLevel.mizerReef()
   (R/reef-project_methods.R), which sets intake_max <- Inf for
   satiation == FALSE species before calling mizer's standard Holling
   type II feeding-level calculation -- so satiation=FALSE forces
   feeding_level to 0 (unlimited intake, used for carnivores since
   predation is refuge-regulated instead), and satiation=TRUE gives a
   real, bounded, whole-diet feeding level (used for herbivores/
   detritivores). Critically: feeding_level is a WHOLE-DIET quantity
   (computed from a species' total encounter across prey + algae +
   detritus + plankton combined), not something computed separately
   per resource -- this needed stating explicitly since it's easy to
   misread the per-resource formulas as if f_i(w) were resource-
   specific. vignettes/model-description.Rmd's existing "Consumption
   and satiation" section (lines ~215-236) was already accurate and
   didn't need fixing.

   Full roxygen audit (not just the one spot flagged in round 1) found
   TWO real pre-existing doc/code mismatches, both present on main
   unchanged, both confirmed against the actual function bodies (not
   just doc comments -- learned that lesson the hard way in round 1,
   see below):
     - getDetritusProduction()'s displayed p_D,f formula was missing
       the (1-f_i(w)) factor that its code has always applied. Fixed:
       added the term, explained why (detritus's feces term uses the
       same feeding-level-adjusted rate as detritus_consumption()/
       getDetritusConsumption(), consistently, unlike algae).
     - getAlgaeConsumption() used @inheritSection to borrow
       algae_consumption()'s formula (no feeding level) -- wrong for
       itself specifically, since getAlgaeConsumption()'s OWN code

ALGAE/DETRITUS STANDING BIOMASS IS ESSENTIALLY ZERO ON ALL THREE
BUNDLED MODELS. algae_biomass(caribbean_3_model) and
detritus_biomass(caribbean_3_model) both return 5.870785e-11 (grams
per square meter). caribbean_10_model and claude_10_model both return
1.143228e-10 for both resources. detritus_lifetime(caribbean_3_model)
is 2.18e-13 years (~6.9 microseconds) - called directly in
extension_mechanism.Rmd's own demo chunk, so this number is already
visible in that vignette's rendered output.

Confirmed this is NOT simply "not converged": dB/dt = 0 exactly for
both resources on caribbean_3_model (checked via the same
production-vs-consumption balance the test suite already uses -
getAlgaeProduction() and getAlgaeConsumption() agree to full displayed
precision: both 86.87579; detritus's is 1.7e-13, i.e. numerical
noise). The reason it's self-consistent despite the absurd absolute
value: getAlgaeConsumption()/getDetritusConsumption() multiply a
mass-specific rate by params@other_params$algae_params$rho, which is
tuned to ~1e13-1e14 (checked directly - e.g. rho values for inverts'
detritus consumption range from 3.3e13 to 5e14 across the size range)
- i.e. rho and the standing biomass are exactly inversely
proportional, and whatever tiny placeholder the biomass got left at,
rho was tuned to compensate, so the encounter rate rho*B (the only
thing that's dynamically meaningful) stays sane even though B itself
does not. rescale_algae()/rescale_detritus() exist specifically to
correct this (multiply biomass by a factor, divide rho by the same
factor, leaving all dynamics unchanged) - so this looks fixable in
principle, but changes what's stored in the bundled .rda files, so
not something to do without sign-off.

Why this matters: caribbean_3_model-description.Rmd's rendered output
literally states "the total algal biomass per square meter is B_A =
5.87e-11 grams" and "total detrital biomass per square meter is B_D =
5.871e-11 grams" right next to a table of real fish biomass_observed
values in the 30-110 g/m^2 range - the contrast reads as obviously
wrong to any reader, even though the underlying dynamics are
internally consistent.

UPDATE (28/07, same session, later): traced this to its exact
mechanism rather than just a hypothesis. It is NOT specific to these
three old bundled objects - it will happen to ANY mizerReef model
built via the package's own documented tuning recipe
(vignette("mizerReef")'s "Tuning the steady state" section,
steady-state-recipe.Rmd), silently, every time, unless the user
separately thinks to call rescale_algae()/rescale_detritus() (which
is never mentioned in either of those two documents). The mechanism,
confirmed step by step:

1. newReefParams() creates the algae/detritus components via
   mizer::setComponent(..., initial_value = 1, ...) (R/newReefParams.R)
   - a hardcoded literal, unrelated to anything about the specific
   model being built. Confirmed empirically: algae_biomass(params) is
   exactly 1 immediately after newReefParams(), and stays exactly 1
   through any number of reefSteady() calls on their own (verified:
   two consecutive reefSteady() calls on a freshly-built params object
   left algae_biomass() at exactly 1 - reefSteady() forces
   other_dynamics to "constant_dynamics" for every other-component
   while the fish species converge (R/reef-steady.R), so B_A/B_D are
   literally frozen throughout that call; the tuneUR()/tuneUR_cc()
   call reefSteady() makes afterwards only sets the *growth rate* to
   match whatever B_A currently is, and never touches B_A itself).

2. calibrateReefBiomass() - a required step in the documented tuning
   recipe, used to bring the freshly-constructed model's fish
   abundance in line with real biomass_observed data - computes
   factor = observed_total / model_total from FISH biomass alone, then
   calls scaleReefModel() (R/reef-components.R). scaleReefModel()
   multiplies params@initial_n_other[[res]] by that same `factor` for
   EVERY other-component (algae and detritus alike), paired with
   dividing rho by the same factor - by design, this is the same
   paired multiply-B/divide-rho transformation rescale_algae()/
   rescale_detritus() perform deliberately, and mirrors how mizer's
   own scaleModel() rescales cc_pp/kappa alongside fish abundance to
   keep encounter rates internally consistent after a calibration
   rescaling. It is doing exactly what it is supposed to do for
   internal consistency - the problem is only that `factor` is
   entirely a fish-abundance-calibration artifact with no relationship
   to what a sensible absolute B_A should be, and B_A started at the
   arbitrary placeholder 1, so the product can land anywhere.

3. Confirmed empirically end to end: building a fresh caribbean_3-style
   params object from caribbean_3_species/caribbean_3_interaction/
   tuning_profile, algae_biomass() is 1 right up until the first
   calibrateReefBiomass() call, which alone drops it to 1.95e-12 (a
   ~5x10^11 factor - i.e. the raw, uncalibrated fish abundance this
   model starts with is about 5x10^11 times too high relative to real
   observed biomass in grams, which is an unremarkable, expected
   magnitude for mizer's generic default abundance scale before
   calibration). Replaying a simplified version of the rest of the
   documented recipe (a few more calibrateReefBiomass()/matchBiomasses()/
   matchReefGrowth()/reefSteady() iterations, then switching to the
   competitive refuge method and re-iterating) landed at 4.02e-11 -
   the same order of magnitude as the real bundled caribbean_3_model
   (5.87e-11); the small remaining difference is because the actual
   calibration script iterates more times and with more nuanced
   reproduction-level tuning than this simplified replay. This is
   airtight confirmation of the mechanism, not just a plausible story.

So: not a bug in the sense of broken/inconsistent dynamics (rho and
growth are correctly tuned for whatever B_A ends up at, every time,
exactly as designed), but a genuine design gap in the documented
tuning workflow - calibrateReefBiomass() implicitly re-scales the
resource pools' absolute magnitude as a side effect of fish-biomass
calibration, and nothing in the recipe ever gives them an independent,
meaningful absolute scale. Every future model built by following
mizerReef's own tuning instructions as written will have this same
issue by default.

Not fixed. Options considered: (a) leave the mechanism as-is but add a
step to the documented tuning recipe (both vignette("mizerReef") and
steady-state-recipe.Rmd) calling rescale_algae()/rescale_detritus() to
a chosen sensible absolute value before the final save, and
retroactively rescale the three bundled models the same way
(reversible, well-tested, no dynamics change - rescale_algae()/
rescale_detritus() exist for exactly this); (b) change
calibrateReefBiomass()/scaleReefModel() itself so algae/detritus are
excluded from the factor rescaling (i.e. keep B_A/B_D fixed and let
rho absorb the whole calibration adjustment on its own) - a real code
change to a documented, tested function, not just a vignette/data
fix, so needs more thought about whether that changes anything else
relied upon; (c) leave as-is entirely (mathematically correct, just
cosmetically odd, could add a caveat sentence to the model-description
vignettes instead).

need fixing; the absolute numeric scale does. ***
